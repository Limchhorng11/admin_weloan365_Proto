# Chat

## Two distinct discussion types, each with its own permission

Chat is now built around two genuinely different kinds of conversation:

- **Officer chat** — a 1:1 thread between a customer and their own assigned loan
  officer.
- **Customer Support** — a shared team channel where any officer holding a seat can
  answer any customer in it, replying under one shared identity ("NHFC Support")
  instead of their own name.

Holding a Customer Support seat is a **channel-level permission**, not a
per-conversation assignment — there is no "Unassigned" state. An officer either has
a seat (and can answer every conversation in the channel) or doesn't.

## Strict read-privacy — applies to every role, no exceptions

A conversation's messages are visible only to people who are actually a party to
it — the customer, their own officer (Officer chat), or an officer holding a seat
(Customer Support). This applies identically to **every role, including Admin**:
Admin manages who holds a seat but cannot read or reply to conversations without
holding one themselves. There is no oversight/masked-view exception.

Each user's own conversation list is filtered to exactly what they can
participate in — an officer never sees another officer's customers, not even
greyed out.

## Admin's Chat page now matches the officer-style layout

Previously, Admin (who never personally participates in any conversation) saw a
special single-section "manager" view. Admin now gets the same two-pane layout
(conversation list + thread) that any officer sees, just with an empty inbox —
the "Officer chat" and "Customer Support" groups both show in the sidebar (Officer
chat reads "No officer conversations yet." when empty), and the thread pane shows
the standard "Nothing to show here" placeholder. The single-section collapse is
now reserved for roles with genuinely nothing to do (no conversations *and* no
manage permission).

## Assign officer — centered dialog, role → officer picker

The "Assign officer" action (top of the Customer Support group, and in the
sidebar header when the group is otherwise empty) opens a **centered modal
dialog** — not an anchored dropdown, since an anchored popover placed inside a
`backdrop-blur` header get clipped to that ancestor's box instead of the full
viewport. The dialog is rendered through a React portal straight into
`document.body` to avoid that class of bug entirely.

Inside the dialog:
- **Select role**, then click one of that role's officers (shown as chips) to
  grant or revoke their seat — the chip toggles instantly, no separate confirm
  step.
- Below that, the full **"Officers answering this channel"** roster is shown as a
  table (**Officer / Role / Branch** columns) with a remove (×) action per row.
- A **Done** button in the footer closes the dialog (alongside the × and
  backdrop-click).

## UI cleanups

- Removed the **"Officer: {name}"** chip from the Officer chat thread header, and
  the small assignee line under each Officer chat row in the sidebar list — both
  were redundant (you only ever see your own name there).
- Removed the **"Replying as …"** identity banner above the composer, for both
  channels.
- Removed the **profile/Info icon** from the thread header for **Customer
  Support** threads (a support conversation isn't tied to one officer's own
  customer relationship, so the shortcut didn't apply) — Officer chat threads
  keep it.
- Sidebar widened from `20rem` to `26rem` to give the roster table room to
  breathe.

## Customer — Chat permissions simplified

- Removed `chat.officer` ("Access Officer chat") and `chat.support` ("Access the
  Customer Support channel") entirely — channel visibility is now driven purely
  by actual participation (assignee match / seat membership), not a separate
  toggle.
- Remaining permissions: **`chat.view`** ("View the chat") and
  **`chat.support_assign`** ("Assign to customer support channel", sensitive,
  requires `chat.view`).
- All 4 system roles re-verified against this simplified set: Admin has both (via
  `"*"`); Senior Officer, Credit Officer, and Customer Service each have only
  `chat.view`.

**Files touched:** `app/chat/page.tsx`, `lib/data.ts`

# Customer — All Accounts

## Reactivate a self-deleted account

A customer who deleted their own account from the mobile app (`accountStatus:
"suspended"`) can now be restored by an admin — e.g. the deletion turns out to
have been accidental.

- The Action column shows an **"Active"** button for inactive rows (in place of
  the previous "—"), gated behind a new permission.
- Clicking it opens a confirmation dialog ("Activate this account?") explaining
  what restoring does before committing — no accidental one-click restores.
- Confirming clears `accountStatus`/`deletedAt`, immediately restoring the row's
  branch, device, and loan-history columns and re-enabling **Change PIN**.

## New permission: "Allow active customer account"

- New `customer.reactivate` permission (sensitive, category **Customer — All
  Accounts**, requires `customer.view`).
- Not granted to any of the 3 non-admin system roles by default — only Admin (via
  `"*"`) can reactivate an account, since restoring a customer's access is a
  compliance-sensitive action.
- Without the permission, the Action cell shows a plain "—" (desktop) / "No
  actions" (mobile), same as before this feature existed.

**Files touched:** `app/customer/accounts/page.tsx`, `lib/data.ts`
